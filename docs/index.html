01 · 最省力

交給 AI 代理處理

如果你不熟 Docker 或指令列，這是最省力的路：準備檔案 → 複製 Prompt → 貼給 AI 代理。它會先問你幾個問題，然後把建檔、改 Dockerfile、建置、驗證整套做完。

STEP 1複製下方的 Prompt，原封不動——裡面已經寫好檔案要去哪裡抓。
STEP 2貼給有檔案與終端機權限的 AI 代理。
STEP 3回答它問的 3 個問題：資料夾、啟動方式、版本號。其餘交給它。

要複製的 Prompt

原封不動複製就能用——裡面已經寫好三個檔案去哪裡下載、開工前要問你什麼、每一步要驗證什麼，以及四條不准踩的紅線。

◆
什麼樣的 AI 代理可以用？ 要能讀寫你電腦上的檔案並執行終端機指令的那種，例如 Claude Code、Cursor、Codex CLI、Gemini CLI、GitHub Copilot Agent。純聊天視窗的 AI 沒有這些權限，但仍可以把 Prompt 貼進去，讓它一步一步指導你手動操作。

檔案在哪裡（想自己先放好的話）

Prompt 裡已經寫好 GitHub 網址，AI 代理會自己去抓，含完整 4,362 條字典——不需要自己萃取翻譯。如果你想先放好，或你的 AI 代理沒有連網權限，就從這裡拿：

02 · 概念

這是什麼：30 秒理解

LiteLLM 是一棟原廠進口的英文展示館。我們沒有動它的一磚一瓦，只請了三位幫手進駐。

📖

字典dict.json

約 4,300+ 條「英文原句 → 中文譯句」的對照手冊，例如 "Virtual Keys": "虛擬金鑰"。這是唯一需要長期維護的檔案。

🗣️

翻譯員inject.js

一段極小的 JavaScript。開頁時先把整頁翻一遍，接著持續盯著畫面，新冒出來的英文立刻查字典換掉。也懂句型——Page 3 of 10 會變成「第 3 頁，共 10 頁」。

🧵

裝訂工人patch_ui.py

建置映像檔時執行一次，把字典和翻譯員縫進管理介面的每一頁 HTML，並把舊版由伺服器渲染的登入頁直接改成中文。

為什麼不直接改原始碼？

做法結果
改 LiteLLM 原始碼 官方每次更新，改過的地方全部要重做，維護成本極高，還容易衝突。
等官方出中文版 目前沒有正體中文介面。
字典注入（本做法） 完全不動原始碼；升級時字典照常沿用；新增的英文字頂多先顯示英文，系統功能完全不受影響。
✦
核心優點：優雅降級（graceful degradation） 就算某句話字典裡沒有，畫面也只是顯示原本的英文，系統一切正常。最壞情況就是介面變回英文——因為從未修改 LiteLLM 本體。

適合誰

想把 LiteLLM 介面變成正體中文（或任何語言）的人 不想每次官方升級就把翻譯重做一次的人 只有 Docker 環境、希望「一次設定、長期沿用」的人

換語言只要替換字典內容即可，inject.js / patch_ui.py / Dockerfile 幾乎不用動。以下以正體中文（zh-TW）為例。

04 · 長期沿用

日常維護：3 個場景

部署完之後你只會碰到這三件事，每件都不到一分鐘。

A · 發現某處還是英文（字典漏字）

  1. 把畫面上那句完整的英文抄下來（大小寫、標點都要一模一樣）。
  2. 打開 zhtw/dict.json，加一行："那句英文": "你的翻譯",
  3. 重新建置：docker compose build && docker compose up -d
  4. 瀏覽器按 Ctrl + F5，確認該處變成中文。
◆
抄英文時，句中連續的空白會被視為一個空白（系統會自動壓縮），所以中間多幾個空格沒關係，但字要完全相同。

懶人版：把這段丟給 AI 代理

B · 升級 LiteLLM 版本

  1. 改 Dockerfile 第一行的版本號（例 v1.93.0 → 新版本）。
  2. docker compose build && docker compose up -d
  3. 新版新增的介面文字會暫時顯示英文——這是正常的優雅降級，不是故障。照〈A〉補進字典即可。

C · 翻譯要修正

直接在 dict.json 找到那句英文，改冒號後面的中文，重新 build 即可。

▲
想還原成英文？ 把 docker-compose.yml 的 build: . 與 image: 兩行改回官方 image（image: ghcr.io/berriai/litellm:v1.93.0），docker compose up -d 即可完全還原。資料庫、金鑰、設定全都不受影響。

關鍵設計決策

設計做法為什麼
冪等 if "zhtw-i18n" in s: continue 重跑 build 不會重複注入。
防提前關閉最容易踩的雷 payload 裡所有 </ 換成 <\/ 字典是內嵌在 <script> 裡，資料中若出現 </script>（或任何 </）會讓 HTML parser 提前關閉 script。而在 JS/JSON 字串裡 <\/ 與 </ 完全等價。
失敗即停 assert count > 0 官方哪天改了 UI 路徑，build 會直接紅燈，而不是默默產出一個沒翻譯的 image。
精確比對優先 正規化空白後查表，查不到才套 RULES 零誤譯風險。代價是被框架拆成多個文字節點的句子查不到。
長度上限 key.length > 300 跳過 避免拿長段落去做無意義的字典查詢。
版本釘選 FROM …:v1.93.0 用 latest / main-stable 會讓某次 build 悄悄換版，導致字典對不上、大量文字回退英文。
◆
版本釘選小抄 LiteLLM 的 ghcr 標籤現在用純版本號（如 v1.93.0）；舊的 main-v<版本> 命名大約停在 v1.66。想查有哪些 tag 可用 docker manifest inspect 逐一探測。

字典是怎麼做出來的

1 · 萃取從官方原始碼對應版本 tag 的 ui/litellm-dashboard/src，用正則撈出所有 UI 字串常值（約 4,300+ 條）。
2 · 翻譯交給 LLM 分批平行翻譯，並使用固定術語表確保全站一致（Virtual Key→虛擬金鑰、Spend→花費…）。
3 · 輸出合併去重，json.dumps(indent=0, sort_keys=True, ensure_ascii=False)——每行一條、依字母排序，方便日後 diff。

升級補字流程

docker cp 匯出新舊兩版 image 的 out/ → 抽取字串常值取差集 → 機械過濾雜訊（Tailwind class、SVG path、程式碼片段；注意別誤殺以引號開頭的 placeholder 範例）→ 交 LLM 翻譯新增部分 → 併回 dict.json。

07 · FAQ

常見問題

改了字典後畫面沒變？
先確認有重新建置：docker compose build && docker compose up -d，再按 Ctrl + F5 清快取。瀏覽器快取是最常見的原因，開無痕視窗可以快速排除。
會拖慢系統嗎？
不會有可感知的影響。翻譯發生在你自己的瀏覽器裡，查字典是雜湊表 O(1) 瞬間完成；伺服器端（API 本體）完全沒被更動。
API 回覆的內容也會被翻譯嗎？
不會。這套機制只翻管理介面的畫面文字，模型回答與 API 資料完全不受影響——CODE / PRE / TEXTAREA / contenteditable 都在保護名單裡。
萬一整個中文化壞掉怎麼辦？
最壞情況就是介面變回英文，功能一切正常。因為從未修改 LiteLLM 本體，把 docker-compose.yml 換回官方 image 即可完全還原，資料庫與金鑰都不受影響。
能翻成簡體 / 日文 / 其他語言嗎？
可以。只換 dict.json 的內容（以及 inject.js 裡 RULES 的句型），其他檔案完全不用動。
升級 LiteLLM 之後會不會整個爛掉？
不會。已實測跨版本升級：改 Dockerfile 的版本號、重新 build 即可。新版新增的字串會暫時顯示英文，補字典就好。真正會讓它失效的只有一件事——官方改掉 UI 匯出路徑，而那種情況 assert count > 0 會讓 build 直接失敗提醒你。
可以不用 Docker 嗎？
原理可以，但本文流程綁在 docker build。若是 pip 安裝的 LiteLLM，等同於在套件目錄手動跑一次 patch_ui.py；缺點是每次 pip install -U litellm 都要重跑，而且沒有映像檔那種「隨時還原」的乾淨性。
